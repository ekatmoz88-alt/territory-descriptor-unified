# PPO Territory — Lifecycle, Updates and Operational Support

## Lifecycle terminology

The available materials refer to development and acceptance stages using abbreviations including ТП, РКД, ПИ, ГИ and acceptance/literature designations such as О1. ПЭО also appears, but its expansion is not asserted because the primary definition has not yet been verified.

## Chronology

Some materials refer to work during 2014. A reliable stage-by-stage calendar, including exact dates, acceptance acts, responsible persons and approvals, requires the original schedule and acceptance documents.

## Update publication and installation

The supplied operational regulation states that:
- the contractor publishes update files and installation instructions on `sd.reksoft.ru`;
- each update is accompanied by information about changes in PPO Territory and corrected defects;
- responsible employees of the regional FMS authority are notified by email;
- contractor representatives perform update installation in the regional authority within one working day after publication.

This is a documented historical support procedure. It does not establish that the website or support arrangement is currently operational, nor does it identify a particular update package or installed build.

## Operational support

The regulation assigns regular support activities to designated employees of the regional FMS authority, following the supplied PPO Territory documentation. When needed, the responsible employee contacts the contractor's technical support.

The source lists these historical support channels:
- website: `https://sd.reksoft.ru`;
- forum: `http://ufms.reksoft.ru/forum`;
- telephone: `8 (800) 333 0340`;
- email: `sd@reksoft.ru`.

These are preserved as historical source references, not verified current contact details.

## Backup operations

The regulation states that responsible regional employees regularly monitor correct operation of the PPO Territory backup facilities, following the supplied documentation. It does not identify:
- backup software or storage topology;
- backup frequency or retention;
- full/incremental strategy;
- encryption or access-control model;
- off-site copy or disaster-recovery site;
- recovery time objective (RTO) or recovery point objective (RPO);
- restore-test schedule or results.

Do not infer that a backup system is effective merely because backup monitoring is specified. Evidence of successful restore tests is required.

## Deployment and rollout activities

The supplied tables describe implementation and rollout activities including:
- survey of technical infrastructure;
- installation and configuration of server software;
- installation and configuration of PPO Territory;
- creation of user and organizational-unit accounts;
- administrator and key-user training/consultation;
- work at listed sites;
- configuration of client workstations;
- enabling application-level access;
- ensuring full application startup;
- on-site user consultations.

These are activities in an implementation/support process, not evidence that each activity was completed at every site.

## Evidence required for a verified lifecycle

- Stage name and contractual deliverable.
- Planned and actual start/end dates.
- Acceptance or review document identifier and date.
- Responsible organization and role.
- Update package version, publication date and installation record.
- Test type, scope and result.
- Backup job status and successful restore-test evidence.
- Source document and page reference.

Do not infer exact dates, acceptance acts, update versions or successful backup restoration from a partial table or ambiguous scan.
