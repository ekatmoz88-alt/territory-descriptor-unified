Deshifrator Architecture

Application purpose, components, domain models, and external integrations.

Document status. This description is based on available project materials and selected code fragments. Unverified details and modernization proposals must not be interpreted as completed implementations.

Purpose and scope

Deshifrator is a standalone desktop application for searching and processing person and case records. Its main functional areas include:

  • WPF/WinForms user interface;
  • person and dossier search;
  • domain models for cases, documents, addresses, and comments;
  • SOAP integration described in project materials; the available mobile-module configuration contains a UMMS endpoint;
  • address search using FIAS data and Elasticsearch;
  • import, export, and synchronization with a mobile module;
  • removable-media operations;
  • print-view generation and MRZ processing;
  • logging and configuration.

Architecture boundary

Separate architecture. ПОСС, ПОМС, and ПОШ ВБД belong to a separate architecture and are not part of the Deshifrator workstation. Their components, relationships, interfaces, and functions are excluded from Deshifrator diagrams and documentation unless their inclusion is explicitly confirmed.

User interface

The available materials mention App, MainWindow, LoginWindow, and ConfigWindow. The main window combines search, pagination, dossier tabs, import/export, and synchronization. The configuration window is intended for integration settings, result limits, and display options.

Network operations should not block the UI thread. Requests should support cancellation and appropriate exception handling.

Domain models

The project materials describe CaseModel (identifier, dossier, comments, dates, and status), DossierModel (person, document, address, case, and processing-state data), FirstScenarioData (document-issuance scenario parameters), AddressSearchModel (address-search criteria), and DocumentSearchModel (document-search criteria).

Internal model identifiers should not automatically be treated as identifiers from external directories or services without checking the relevant contract.

SOAP integration

The project documentation lists the following operations:

  • GetPersonAddresses
  • GetPersonDocuments
  • GetCountryDictionary
  • GetDocumentDetail
  • GetAddressDetail
  • GetPersonCasesInfo
  • IssueNewDocument
  • RollbackIssueNewDocument
  • SearchPersonFile

The package configuration review found a UMMS SOAP endpoint in ModuleMobile.exe.config; no such endpoint was found in Descriptor.exe or ModuleStationary.exe configuration. The ownership of the listed SOAP operations by a specific executable therefore requires verification against source code and the WSDL.

When migrating the SOAP client or changing the integration, compatibility with the actual WSDL must be preserved: SOAPAction, namespaces, wrapper elements, and data types. Historical XML element names may be part of the wire contract; renaming them is acceptable only after contract verification and compatibility checks on both sides.

HttpClient, XmlSerializer, explicit SOAP-envelope construction, asynchronous calls, and CancellationToken were considered as modernization approaches. This describes potential approaches, not a completed migration.

Address search

Address search is associated with FIAS data and Elasticsearch. Production node addresses, index names, and access parameters are excluded from this public documentation.

Key integration concerns include request serialization, parameter encoding, timeouts, HTTP-status handling, and response-structure validation. An engine-version upgrade should be treated as a separate migration task.

External dependencies

The package includes SOAP configuration for the mobile module, local FIAS/Elasticsearch configuration for the mobile and stationary modules, SQLite, file exchange with the mobile module, removable-media operations, printing components, and Tesseract OCR. Not all dependencies belong directly to Descriptor.exe.

Service addresses and environment parameters should be stored outside source code. Public examples use fictional addresses only, such as https://service.example.invalid/soap.

Evidence limitations

This documentation is based on available descriptions and selected code fragments. A complete specification requires verification against the current source code, WSDL, build configurations, and mobile-module implementation. The completeness of any .NET 8 migration, current versions of external components, and all business-process state transitions have not been confirmed.
