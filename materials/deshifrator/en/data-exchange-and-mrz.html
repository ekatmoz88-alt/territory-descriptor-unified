File Exchange with the Mobile Module and MRZ

File contract, processing states, encryption, printing, and MRZ.

Document status. This description is based on available project materials and selected code fragments. Unverified details and modernization proposals must not be interpreted as completed implementations.

Purpose of the exchange

The application architecture includes data exchange with a separate mobile module. Transfer is performed through files on removable media; the available materials describe XML serialization and data encryption.

File contract

The historical implementation mentions the following file names:

  • dat.umms
  • datMM.umms
  • datsynch.umms

The exchange uses the TransferModel and TransferDossierModel models, while operations are coordinated by the TransferManager component.

File names are included as technical format identifiers. Real file contents, personal-data examples, production exports, and encryption keys are not published.

Processing states

The materials list the following dossier states: Created, Exported to mobile, Synchronized, and Error. State transitions may be implemented in calling code rather than exclusively inside the exchange component. Reconstructing the complete state machine requires reviewing all call sites and result handlers.

Compatibility and reliability

Both sides of the integration must be considered when changing the exchange format. Practical requirements include explicit format versioning, integrity and structure validation, file-size limits, safe error handling, atomic writes, duplicate-import protection, and logging that excludes personal data.

Changing the encryption algorithm or serialized model structure without coordination with the mobile side may prevent previously created files from being read.

Encryption

The available materials associate the StringCipher component with encryption of exchange files. This public documentation does not disclose secret parameters, keys, salt, IV, passwords, or test values from the source code.

For modernization, a versioned cryptographic container and authenticated encryption with integrity verification are recommended. The specific algorithm and migration plan must be agreed with the mobile client and checked for compatibility with historical data.

Printing and MRZ

The PassportPaint component contains print-view and MRZ-generation logic. The materials identify a two-line MRZ format with 44 characters per line (2×44), as well as separate transliteration logic.

Changes should be validated for line length, permitted characters, transliteration rules, dates, and check digits against the applicable edition of ICAO Doc 9303. This description records the existence of the functional area; it does not replace formal validation of every document type.

Demonstration data

Public examples must use synthetic records with fictional names, document numbers, addresses, and identifiers only. Do not use real MRZ strings, scans, photographs, dossiers, or exports.
